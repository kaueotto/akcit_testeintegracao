# Prompt type 3: API contract and test data (data-driven)

**Prompting technique:** zero-shot in v1. v2 uses an **expert persona**, names the **test design techniques** to apply (equivalence partitioning and boundary value analysis), fixes the initial state and asks for **structured output (JSON with a schema)**, so a test can consume the response directly.

**Goal:** get a large, diverse data set for the `POST /pedidos` contract, with expected values that are computed rather than "plausible".

---

## v1: naive (zero-shot, no context)

```text
Gere dados de teste para a API POST /pedidos.
```

LLM response: [respostas-llm/03-dados-v1.md](../respostas-llm/03-dados-v1.md)

## v2: refined (persona + techniques + fixed state + JSON schema)

> `{{CONTRATO}}` is replaced with the full content of [docs/contrato-api.md](../docs/contrato-api.md).

```text
Atue como especialista em testes de contrato (consumer-driven contracts) e em técnicas de projeto de teste (partição de equivalência e análise de valor-limite).
<contrato>
{{CONTRATO}}
</contrato>

## Tarefa
Gere uma massa de dados para testar o CONTRATO do endpoint POST /pedidos de forma data-driven. O estado inicial do estoque é FIXO e é este:
[{"id":"P1","nome":"Teclado","preco":150.5,"quantidade":10},{"id":"P2","nome":"Mouse","preco":80,"quantidade":5},{"id":"P3","nome":"Monitor","preco":1200,"quantidade":0}]
Cada caso é executado isoladamente, partindo desse estado inicial.

## Regras
- Aplique partição de equivalência e valor-limite em: cliente, itens (lista), produtoId, quantidade (0, 1, limite do estoque, limite+1, negativo, decimal, string, null) e tipos JSON errados.
- Inclua casos de sucesso com o `total` esperado calculado corretamente (mostre o cálculo no campo "justificativa").
- Use SOMENTE os status codes do contrato.
- Para respostas 201, informe também o estoque esperado de cada produto afetado após a requisição.

## Formato de saída
Responda APENAS com um array JSON válido (sem markdown, sem comentários), em que cada elemento segue exatamente:
{"id": "CT-01", "descricao": string, "tecnica": "particao" | "valor-limite" | "contrato", "corpo": <qualquer JSON enviado como corpo>, "statusEsperado": number, "totalEsperado": number | null, "estoqueEsperado": {"P1": number, ...} | null, "justificativa": string}
Gere entre 15 e 20 casos.
```

LLM response: [respostas-llm/03-dados-v2.json](../respostas-llm/03-dados-v2.json)

## v3: adjusted after analysing the v2 output

Problems found in v2 and the adjustment made for each:

| Problem in the v2 output | Adjustment in the prompt |
|---|---|
| `estoqueEsperado` came back `null` on every error, so the compensation check (e.g. "P1 must go back to 10") ended up only in the free text of `justificativa` and could not be automated | `estoqueEsperado` is now **mandatory in every case**, including errors |
| No boundary values for `cliente` (`""`, spaces only) | The missing partitions are listed explicitly |
| The `total` only exercised "easy" values (150.5, 80) | Two products added with "tricky" prices (`0.1`, `1.005`) and floating-point cases requested |

```text
(same persona, contract and task as v2, with these changes:)

O estado inicial do estoque é FIXO e é este:
[{"id":"P1","nome":"Teclado","preco":150.5,"quantidade":10},{"id":"P2","nome":"Mouse","preco":80,"quantidade":5},{"id":"P3","nome":"Monitor","preco":1200,"quantidade":0},{"id":"P4","nome":"Clipe","preco":0.1,"quantidade":100},{"id":"P5","nome":"Parafuso","preco":1.005,"quantidade":10}]

## Regras
- Aplique partição de equivalência e valor-limite em: cliente (ausente, vazio "", só espaços, tipo errado), itens (ausente, vazia, elemento null, tipo errado), produtoId (vazio, inexistente, tipo errado), quantidade (0, 1, limite do estoque, limite+1, negativo, decimal, string, null).
- Inclua casos de sucesso com o `total` esperado calculado corretamente (mostre o cálculo no campo "justificativa").
- Inclua pelo menos 2 casos com armadilhas de ponto flutuante no total (ex.: 0.1 × 3; 1.005 × 1), usando arredondamento comercial (half-up) para 2 casas.
- Inclua pelo menos 2 casos de falha no MEIO de um pedido com vários itens, para verificar a compensação.
- Use SOMENTE os status codes do contrato.
- `estoqueEsperado` é OBRIGATÓRIO em TODOS os casos (inclusive erros): informe a quantidade de cada produto citado no corpo após a requisição. Em erros, isso prova que a validação não tocou o estoque ou que a compensação devolveu as reservas.

## Formato de saída
(same JSON array, with "estoqueEsperado": {"P1": number, ...} never null)
Gere entre 20 e 25 casos.
```
